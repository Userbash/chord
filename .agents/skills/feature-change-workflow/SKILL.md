# Feature Change Workflow

Провести крупное изменение до результата в пределах разрешённого scope. Учитывать ранее выданное разрешение на предложение, документацию и реализацию; не требовать отдельного подтверждения каждого этапа, если дальнейшая работа уже разрешена.

Остановиться для решения пользователя, только если он запросил такую остановку, появился существенный неразрешённый выбор, расширение scope или действие вне текущего разрешения. Явный запрос только на план или документ не разрешает реализацию.

## Этап 1. Предложение

1. Изучить текущую рабочую область, ближайшие `AGENTS.md`, существующие документы, похожую реализацию и рабочее состояние. Если задача находится внутри Git-репозитория, проверить его branch, status и diff.
2. Подтвердить реальный scope и отделить обязательный результат от возможного расширения.
3. Выявить критичные для домена инварианты, например безопасность, авторизацию, идемпотентность, транзакционные границы, совместимость и восстановление, если они относятся к задаче.
4. Если существует архитектурный выбор, представить несколько релевантных вариантов с последствиями и рекомендовать один. Не предлагать искусственные альтернативы для существующего стека.
5. Описать архитектуру, данные, интеграции, этапы, проверки, риски и откат без изменения файлов, если ближайшая repo-policy не задает иной формат.
6. Если существенные решения и реализация уже разрешены, продолжить. Иначе представить конкретное предложение для решения пользователя.

## Этап 2. Документация

1. Создать или обновить один canonical Markdown-документ, если этого требует repo-policy, согласованный контракт или необходимость сохранить существенные решения. Использовать существующий документ, если он уже покрывает задачу.
2. Следовать ближайшей repo-policy по имени, языку и tracked/untracked статусу. Если такой policy нет, использовать один локальный русскоязычный документ `YYYY-MM-DD.md`; если он уже существует, обновить релевантный раздел вместо создания второго дневного документа.
3. Зафиксировать цель, подтвержденное текущее состояние, выбранную архитектуру, структуру данных или БД при наличии, этапы разработки, критерии приемки, проверки, риски, откат, принятые решения и out-of-scope, кроме пунктов, которые ближайшая repo-policy явно запрещает или заменяет.
4. Не добавлять непроверенные code examples.
5. Не превращать запись уже согласованных решений в отдельный approval gate. Остановиться на документе, если пользователь именно так ограничил задачу.

## Этап 3. Реализация

1. Повторно проверить актуальные инструкции и пользовательские изменения. Если задача находится внутри Git-репозитория, также проверить branch, status и diff.
2. Реализовать согласованный scope полностью, переиспользуя существующие сущности и паттерны без незапрошенного расширения.
3. Для новых environment variables сначала обновить canonical `.env.example`; обязательные значения проверять fail-fast.
4. В TypeScript не использовать `any`.
5. Ожидать готовность через bounded state checks; использовать delay только как backoff между реальными проверками.
6. Выполнить проверки, соответствующие риску изменения, и обновить статус документа подтвержденными результатами.
7. Показать итоговый diff и незакрытые риски. Не выполнять commit или push без отдельного явного запроса.

## Границы

- Запрос только на документ сам по себе не активирует этот skill. Если workflow уже активирован для крупного изменения и пользователь решил остановиться на документации, закончить после документа.
- Сам факт изменения нескольких файлов не требует этого workflow, если scope понятен, архитектурного выбора нет и отдельные approval gates не нужны. В таком случае использовать короткий inline-план, реализацию и релевантные проверки.
- Не запускать автоматически другие skills, охватывающие весь lifecycle proposal → planning → implementation. Подключать узкий специализированный skill только для отдельного аспекта задачи или по явному запросу пользователя.
- Учитывать недвусмысленное разрешение продолжить или выполнить согласованный scope целиком, включая ранее выданное. Ответ на уточнение сам по себе не расширяет разрешённый scope.
- При новом факте обновить план. Возвращаться за решением пользователя, если меняется существенное согласованное решение, риск или scope; обычные уточнения реализации решать самостоятельно.
- Не создавать несколько плановых документов, skills или новых сущностей без необходимости для текущего scope.
- Не превращать одноразовое решение текущей задачи в глобальное правило или durable memory без явного запроса.
