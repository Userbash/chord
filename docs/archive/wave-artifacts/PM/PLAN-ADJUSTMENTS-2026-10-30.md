## 2. Диагноз: где именно теряется время

### 2.1. Разрывы IPC — не «пять имён», а отсутствие проверки класса

Скан `generate_handler!` против `invoke(`/`invokeFn(` даёт четыре разрыва:

| UI-вызов | Файл | Зарегистрировано в Rust |
|---|---|---|
| `attachments_upload_slots` | `ui/features/composer.js:725` | `request_upload_slots` |
| `create_invite` | `ui/features/invite-modal.js:370` | `create_channel_invite` |
| `pins_list` | `ui/app.js:1372` | `list_channel_pins` |
| `threads_list` | `ui/app.js:1365` | `list_channel_threads` |

Плюс 24 команды зарегистрированы, но UI их не зовёт (`auth_*`, `net_*`, `ready`,
`settings`, `members_page`, `search_page`, `join_guild`, `accept_invite`, `pin_channel_message`
и др.). Часть из них — задел и тестовые входы, часть — мёртвая поверхность.

Почему это повторяется: `tests/meta/ipc-path.test.mjs` сверяет **сигнатуры** команд с
`generate_handler!`, но не сверяет **имена из JS**. Юнит-тесты фронтенда подменяют
`invoke`, поэтому зелёные. Класс ошибок не закрыт ни одним тестом — значит, каждая
интеграционная волна будет ловить его заново.

### 2.2. Два счётчика прогресса противоречат друг другу

- PLAN: **48 / 90** карточек (обновлён 23.10).
- G6: **23 implemented / 41 partial / 27 absent** из 91 функции (обновлён 30.10).
- RW-40: **26 принятых срезов** (30.10), которые не двигают ни один из счётчиков.

Ни один из трёх не является ложью, но вместе они читаются как «прогресс не сходится».
Это и есть причина, по которой новый воркер не понимает, что принято на самом деле.

### 2.3. Приёмка есть, слияния нет

Gate-артефакт привязан к `0239543` (24.10, 10:22). После него принято 26 срезов,
`main.rs` правился в 18:29. `MERGE-READINESS-12` ставит `merge = block` по трём причинам
(F-1, F-3, F-4). Пока дерево грязное:
- md5 приходится пересчитывать вручную, и каждый новый ACCEPT делает прошлые сверки устаревшими;
- «что принято» проверяется на глаз;
- любой новый воркер стартует от неопределённого baseline.

### 2.4. Живого окна нет, и это блокирует не только live

E3 = 0. Следствия: READY/send не проверены; voice MVP не начат (нужны два клиента);
DAVE/MLS и видео не оценены даже грубо; `implemented (live unverified)` — это ярлык,
а не приёмка. Одна живая сессия закрывает сразу READY, rail, send, ack, reconnect
и (частично) voice-idle.

### 2.5. RE перед каждым доменом

Правило «код только после `[L]/[S]/[D]`» само по себе правильное. Дорого обходится
другое: RE запускается **на домен**, а не пакетом, и результат живёт в отчёте волны,
а не в едином реестре контрактов. Отсюда: `POST /typing` и `/invites` пришлось
подтверждать отдельными `[S]`-оракулами уже после старта карточек.

### 2.6. Проверка дороже кода — но не всякая проверка одинаково полезна

Процесс требует red/green, 5 мутаций на срез, независимое ревью, md5, gate. Это ловит
P1 (гонка `settings_save` в INT-03) — то есть работает. Проблема в равномерности:
5 мутаций и два прохода ревью идут и на S-карточку с одним вызовом, и на L-контракт
с криптой. Пропускная способность упирается в ревью, а ревьюеров меньше, чем авторов.

### 2.7. Параллелизм ограничен не только железом

Кроме `target-dir` и общих файлов, есть третий ограничитель — **контекст**:
новый воркер перечитывает `PROJECT-CONTEXT`, `TASKS`, `STATE`, `MERGE-*` и всё равно
получает устаревшую картину (STATE 23.10, db 23.10, PAUSE 24.10, MERGE-READINESS 30.10).

### 2.8. Голос и видео — отдельная физика

Их нельзя проверить без двух живых клиентов. Это не «медленный код», а другой тип
работы: интероп-стенд, а не юнит-тесты. Пока voice идёт в общем потоке, он либо
блокирует очередь, либо принимается «по частям» без end-to-end.

## 3. Корректировки плана

Формат: ID → что меняется → почему не ломает цепочку → файлы → приёмка.
P0 — до следующего merge; P1 — следующий batch; P2 — по мере.

### ADJ-01 (P0). IPC-паритет как мета-тест

**Что.** Новый `tests/meta/ipc-names.test.mjs`:
1. парсит `generate_handler![…]` из `rust/gui-spike/src/main.rs`;
2. собирает `invoke("…")` и `invokeFn("…")` из `rust/gui-spike/ui/**/*.js`;
3. требует `UI ⊆ Rust` — каждый вызов из UI имеет зарегистрированную команду;
4. обратное направление (`Rust \ UI`) — не ошибка, а **отчёт**: список в выводе теста,
   чтобы 24 «спящие» команды не росли молча;
5. red-proof: синтетическая пара «UI зовёт `x`, Rust регистрирует `y`» обязана валить тест.

**Почему безопасно.** Продуктовый код не меняется; тест читает файлы, окно и сеть не нужны;
входит в `test:meta`, который уже есть в `gate:worker`.

**Файлы.** `tests/meta/ipc-names.test.mjs` (новый), строка в §8 `TDD-PLAN.md` (вставка
в §8 — для TL), `TASKS.md` — карточка.

**Приёмка.** На текущем дереве тест **красный** ровно на 4 имени; после ADJ-02 — зелёный;
red/green-логи в `waves/<ID>/`.

### ADJ-02 (P0). Разблокировать merge: 4 имени, приёмка INT-03, gate, коммит

**Что.**
1. Переименовать вызовы в UI под Rust (не добавлять алиасы — алиасы удваивают поверхность,
   как `join_guild`/`enter_guild`, Q-01):
   `attachments_upload_slots → request_upload_slots`, `create_invite → create_channel_invite`,

3. Дать лог `npm run gate:worker` для `G05-REST-MUTATIONS-FIX` (F-3).
4. Сделать интеграционный коммит baseline и прогнать полный gate на чистом дереве (F-4).

**Почему безопасно.** Правка — 4 строки в трёх UI-файлах + тест из ADJ-01. Никаких
изменений контрактов Rust, тестов не ослабляем.

**Файлы.** `ui/app.js`, `ui/features/composer.js`, `ui/features/invite-modal.js`,
`tests/meta/ipc-names.test.mjs`, `waves/db.jsonl`/`STATE.md` — только TL.

**Приёмка.** `npm run test:meta` зелёный; `npm run test:unit` 834+; `gate:worker` exit 0;

### ADJ-03 (P0). Один живой прогон по сценарию, а не «окно для READY»

**Что.** `waves/RW-40/LIVE-WINDOW-RUNBOOK.md` (новый): предполётный offline-чек-лист,
затем один прогон в фиксированном порядке. Каждый шаг — артефакт и стоп-правило.

| # | Шаг | Доказательство | Стоп |
|---:|---|---|---|
| 0 | offline dry-run на фикстурах: `m2-*.e2e` c `CHROME_BIN` | зелёный fixture-набор | нет браузера → шаг 1 не начинать |
| 1 | READY: вход, гильдии, каналы | `READY` без секретов в логе | 401/капча → фиксировать и остановить |
| 2 | rail + переключение канала | скрин + `data-guild-id` | пустой rail → стоп |
| 3 | отправка сообщения + ack | id сообщения, `MESSAGE_CREATE`, read-state | 429 → бэкофф, не ретраить вручную |
| 4 | reconnect: разрыв 3 с | `RESUMED`, счётчик dispatch | повторный IDENTIFY → стоп |
| 5 | invite: resolve/accept | код 200/204, участник в списке | 403 → только фиксация |
| 6 | voice-idle: вход в канал (1 клиент) | `VOICE_STATE_UPDATE`, панель | нет UDP — это ожидаемо, не fail окна |

**Почему безопасно.** Offline-часть выполняется без окна и без сети. Живая — одно окно,
read-heavy, без необратимых действий; секреты не логируются (`P0-03`).

**Приёмка.** Артефакты по шагам, `E3` закрыт хотя бы для READY+send+reconnect; остальное —
явно `unverified`, не «принято».

### ADJ-07 (P1). Глубина ревью по риску, а не по умолчанию

**Что.**
- S-карточка (≤1 контракт, нет FFI/крипты): один независимый ревьюер + чек-лист;
- L/XL, P0/P1, FFI, live-путь: два прохода (как сейчас);
- мутации: обязательны для P0/P1-контрактов; для P2 — выборочно, 1–2 на batch;
- ревью batch-а одним ревьюером, карточки — параллельно;
- P2 не возвращает карточку целиком, а уходит тикетом (уже разрешено `DEVELOPMENT-PROCESS.md` §5).

**Почему безопасно.** Ослабляется не проверка, а её **кратность** для мелких срезов;
запреты (`P0/P1 → return`, автор ≠ ревьюер, тесты не ослаблять) остаются.

**Приёмка.** Метрика: возвраты по P2 не растут, first-pass rate растёт; решение
пересматривается через 2 batch.

## 6. Пересчёт прогноза

Факты, на которых строится оценка:
- 26 срезов принято 24–30.10, **из них 24 — 30.10 одним проходом**: это накопленная
  приёмка, а не дневная скорость; кодирование шло 24–30.10 без коммитов;
- с 24.10 **0 коммитов** — стадия «принято → слито» не работает;
- 4 разрыва IPC и 24 спящие команды — измеримый долг, а не оценка;
- voice: примитивы есть, end-to-end нет; видео нет.

Отсюда:

| Сценарий | Условия | Оценка |
|---|---|---|
| Merge + доверие | ADJ-01/02/05, gate на чистом дереве | 1–2 дня |
| Live MVP (READY/send/reconnect/invite) | одно окно + runbook | 2–4 дня после merge |
| Паритет сети и чата (G-01, M-07, C-02, G-05, P-03) | 2 code slots, без новых доменов | 2–3 недели |
| Voice MVP (2 клиента в канале) | отдельный трек, стенд, Opus/устройства | 3–5 недель, вилка широкая |
| Согласованный scope: сеть + чат + voice MVP | живое окно, без новых доменов | **4–6 месяцев** |
| Все 91 функция (видео, DAVE/MLS, live-стабильность) | нужен интероп-стенд | не оценивается; ориентир > 6 месяцев |

Честная рамка: 4–6 месяцев — это оценка для **согласованного** scope (сетевой клиент,
чат, голос MVP), а не для Discord целиком. DAVE/MLS, видео, вложения и live-стабильность
без окна не оцениваются: у них нет ни одного end-to-end прогона.

## 9. Ожидаемый эффект: ошибки, повторные проходы, токены

Оценки ниже — модель по измеренным фактам, не обещание. Токены считаны по правилу
«2,5–3 символа на токен» для смешанного Markdown/кода; точного токенайзера в окружении нет,
поэтому даны диапазоны. Пересчёт — после двух batch по факту (как требует `PROCESS.md` §3.15).

### 9.1. База для сравнения

| Метрика | Факт | Как измерено |
|---|---:|---|
| Карточек с ≥2 проходами ревью | **16 из 28 (57 %)** | `REVIEW*` по каталогам `waves/RW-40/PM/*` |
| Проходов ревью всего | 27 первых + 15 PASS2 + 5 PASS3 + 3 PASS4 | имена файлов |
| Артефактов ревью/отчётов/приёмки | 217 файлов, 1,04 МБ | `find … -iname` + `wc -c` |
| Gate-прогонов на принятую карточку | **≈2,35** (174 / 74) | `.gate/worker-*.json` |
| Документов на вход воркера | 219 КБ (`PROJECT-CONTEXT` + `TASKS` + `STATE` + `WAVE-PLAN` + `MERGE-READINESS`) | `wc -c` |
| Это в токенах (полное чтение) | **≈70–90 тыс.** | 219 КБ / 2,5–3 |
| Реальное чтение (выборочное) | ≈30–50 тыс. токенов на новую сессию | оценка по структуре доков |
| Поздно найденных IPC-разрывов | 4–5 за интеграционную волну | §2.1, `MERGE-READINESS-12` F-1 |

### 9.2. Что и на сколько меняется

| Метрика | Сейчас | После корректировок | Эффект | Уверенность |
|---|---|---:|---:|---|
| IPC-разрывы, доходящие до merge | 4–5 | **0** | −100 % класса | высокая: детерминированный тест |
| Карточки с ≥2 проходами ревью | 57 % | 30–35 % | −40 % | средняя: зависит от дисциплины ADJ-07 |
| Gate-прогонов на карточку | 2,35 | 1,2–1,5 | −40 % | высокая: правило уже есть, нет дисциплины |
| Токены на вход воркера | 30–50 тыс. | 10–15 тыс. | −65 % | средняя |
| Токены на принятую карточку | 100 % | 65–75 % | **−25–35 %** | средняя |
| Повторные правки после «зелёного» | 100 % | 50–70 % | **−30–50 %** | средняя: только покрытые классы |
| Второй проход fake→live | 100 % | 75–85 % | −15–25 % | низкая: объём работы не исчезает |
| Календарь offline-части | 100 % | 70–80 % | −20–30 % | средняя |
| Live / voice / video | 100 % | 100 % | **0** | высокая: нужен стенд |

Ключевое: **−25–35 % токенов и −30–40 % повторных циклов** — это устойчивый режим после
третьего batch. Первые два batch дают **+5–10 %** накладных: новый тест, baseline-коммит,
разовая синхронизация журнала.

### 9.3. Почему именно столько (причинная цепочка)

- **ADJ-01** убирает не 4 ошибки, а их источник. Один поздний разрыв стоит примерно
  один интеграционный цикл: правка + повторный targeted + ревью + gate. При 4–5 разрывах
  на волну это 10–15 % токенов волны. Тест стоит ~0,1 с и ловит класс навсегда.
- **ADJ-05/ADJ-11** бьют по самой дорогой статье — ориентации. 30–50 тыс. токенов на
  сессию при 2–3 сессиях на batch — это 20–30 % расхода. Свежий `PROJECT-CONTEXT`
  и один журнал сокращают вход в 3 раза.
- **ADJ-07** снимает лишнюю кратность, а не проверку: 57 % карточек с двумя и более
  проходами — это и есть измеренный запас. Цель 30–35 % достижима без роста P0/P1,
  потому что риск-классы (FFI, live, крипта) остаются на двух проходах.
- **Batch-gate** уже предписан процессом, но фактически 2,35 прогона на карточку.
  Приведение к 1,2–1,5 — организационное, не техническое; экономия ~5–8 % токенов
  и заметная доля календаря.
- **ADJ-02** не экономит токены напрямую, но снимает хвостовой риск: пока дерево грязное,
  любая сверка «что принято» делается заново, а неудачная синхронизация стоит недели.

### 9.4. Чего корректировки не исправят

- **Живое окно.** READY/send/reconnect не станут дешевле: нужен один прогон и токен.
- **Voice/video.** Интероп двух клиентов не заменяется тестами; экономия только на
  планировании (ADJ-09), не на работе.
- **Новые классы ошибок.** Мета-тест закрывает IPC, но не логику, не гонки, не контракты
  REST. Для них работает только red-first и ревью.
- **Неизвестные контракты.** RE остаётся стоимостью входа в новый домен; ADJ-06 делает
  её видимой, но не нулевой.

### 9.5. Стоимость внедрения и окупаемость

| Пакет | Работа | Окупаемость |
|---|---|---|
| ADJ-01 + ADJ-02 | 0,5–1 день, один batch | 1–2 интеграционных цикла (3–5 дней) |
| ADJ-05 + ADJ-11 | 0,5 дня, только доки/мета | сразу: минус 1–2 сессии ориентации на batch |
| ADJ-07 | правило + 2 batch наблюдения | со 2-го batch |
| ADJ-03 | 0,5 дня runbook + окно | одно окно вместо трёх попыток |

Суммарно: **2–4 дня setup**, окупается за **3–5 batch** (1–2 недели) при сохранении
текущего темпа приёмки.

### 9.6. Как проверить, а не поверить

Добавить в KPI batch-а четыре числа (сейчас их нет):

1. `review_passes_per_card` — цель ≤1,4;
2. `gate_runs_per_card` — цель ≤1,5;
3. `tokens_per_accepted_card` — из логов агентов, сравнение с базой;
4. `late_findings` — ошибки, найденные после «зелёного» прогона, по классам.

Если через два batch `late_findings` не падают, а `tokens_per_accepted_card` не снижается
на 15 %, корректировки пересматриваются, а не «дожимаются».
