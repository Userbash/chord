# Тест-план Rust-клиента: TDD, конформанс, фикстуры RE

Документ задаёт стратегию тестирования и **каталог тестов**, под которые в проекте Rust будут
написаны функции. Принцип — strict TDD: тест пишется и краснеет до реализации (`PLAN.md`, гейт 4).
Фикстуры — из лаборатории `/home/sanya/re-deep` (санитизированные, без секретов).

## 1. Уровни тестирования

| Ур. | Название | Что проверяет | Где живёт |
|---|---|---|---|
| L0 | Static | формат, линт, типы: `cargo fmt --check`, `clippy -D warnings`, `tsc` | CI/гейт, без рантайма |
| L1 | Unit | чистые функции: ETF/zstd, ключ-i18n, SRTP, плюрализация | рядом с кодом (`#[cfg(test)]`) |
| L2 | Конформанс | байтовые фикстуры RE → ожидаемые структуры (оракул) | `discord-conformance` |
| L3 | Интеграция | собственный стаб-сервер WS/REST/RTC; сценарии-цепочки | `crates/*/tests` (интеграционные бинари) |
| L4 | E2E-smoke | ручной прогон на живом Discord (не в CI): вход, чат, голос | чек-лист `smoke.md` |
| L5 | Fuzz | устойчивость парсеров (ETF, zstd, RTP/SRTP, protobuf) | `cargo-fuzz` |
| L6 | Mutation | Mutation-тестирование: catch rate, разбор survivors/INCONCLUSIVE, restore по md5 | `waves/<ID>/run-mutations*.py` |
| L7 | Приёмочный | Нефункциональный контур: бюджеты ARCHITECTURE §9, security-review, ADR | TL-приёмка волны |

Правила: L0/L1/L2 обязательны на каждый PR; L3 — на волновых гейтах; L4 — только по согласованию
(живой аккаунт не задействуется в CI); L5 — ночной прогон; L6 — на каждой волне с кодом;
L7 — при приёмке batch (производительность, безопасность, решение по рискам).

### 1.0 Матрица выбора уровней

| Тип изменения | Обязательные уровни | Комментарий |
|---|---|---|
| Док-only / план | L0 | meta-тесты синхронности доков |
| Мелкий фикс (S) | L0, L1, L6 | 3–5 мутантов |
| Модуль/парсер (M) | L0, L1, L2, L6 | оракул из RE-фикстуры обязателен |
| Интеграция (L/XL) | L0–L3, L6 | стаб-сервер, сценарии-цепочки |
| UI/платформа | L0–L3, L6, L7 | + бюджеты производительности и security |
| Релиз | L0–L7 | полный контур, живой smoke по окну |

Требование к **оракулу**: тест сверяется с независимым источником (реальный артефакт, jq/awk/md5,
эталонная спецификация), а не с текущей реализацией. Если оракул — сама реализация, это не
конформанс-тест, а регрессия; такие кейсы помечаются явно.

### 1.1 Бюджет тестов и скорость (2026-10-20)

Бюджет защищает от «тестов ради тестов»: каждая карточка проверяет контракт, а не повторяет
соседнюю. Ориентир на одну карточку:

| Размер | Тесты | Мутации | Комментарий |
| --- | ---: | ---: | --- |
| S | 6–10 | 3–5 | один модуль/парсер, 2–3 границы |
| M | 10–16 | 5–8 | типы + reducer/selector, основные ветви |
| L | 16–24 | 8–12 | несколько модулей, stale/duplicate/границы |
| XL | 24–32 | 10–14 | только для P3-02/P3-04 и подобных; дробить |

Исключения фиксируются в `TEST-CORRECTIONS.md` или в отчёте: почему тестов больше (например,
P2-09 — 54 теста из-за трёх модулей и ревью-фиксов). Задним числом тесты не сокращаются.

Правила оптимизации:
- **Targeted, не full.** Воркер гоняет только свои тест-бинарники; `cargo test --workspace`,
  `clippy`, `fmt` и `gate:worker` — один раз на batch в integration-лейне.
- **Табличные кейсы.** Одинаковые границы (статусы, op-коды, формы поля) проверяются таблицей,
  а не копипастой 10 функций.
- **Один оракул на поведение.** Не дублировать проверку того же поля в types/reducer/selectors,
  если один слой уже доказывает контракт; селектор проверяет выборку, не парсер.
- **Общие помощники.** Фикстуры и builder-ы — в `tests/support/`, без копий на 50 строк.
- **Никаких тестов реализации.** Не проверять приватные детали, которые не являются контрактом.
- **Skip-aware.** Нет внешней среды — skip с причиной; skip не считается pass.
- **P3 не блокирует.** Новый P3-тест добавляется только если он закрывает риск; иначе backlog.

Полный gate batch: `cargo fmt --all -- --check` → `clippy -D warnings` → targeted/core →
`cargo test --workspace` → `npm run gate:worker`. Полный прогон не дублируется каждым воркером.

### 1.2 Цикл поиска пробелов (добавлено по RW-28…RW-35, 2026-10-23)

До заморозки ТЗ координатор просматривает последние принятые отчёты и `waves/STATE.md` §7.
Каждый новый риск из ревью, переживший мутант или повторный флак получает один из исходов:
`test ID` в текущем batch, отдельная карточка/решение TL либо явно обоснованное исключение.
Не переносить найденный дефект только как prose-риск, если его можно воспроизвести локальным
тестом. Приоритет усиления: P0/P1/P2 из review; surviving/INCONCLUSIVE mutation; пропуск сценария
в отчёте; затем P3 backlog по вероятности и последствиям.

Для каждого поведения пройти матрицу применимых измерений: обычный путь; нижняя/верхняя граница
и off-by-one; пустое/невалидное/обрезанное значение; дубликат/неверный индекс; error path и
cleanup; повторный вызов; владение ресурсами; параллельность/порядок событий; среда отсутствует,
отказывает или явно включена. Не добавлять неприменимые кейсы ради заполнения матрицы.

Оракул должен быть независим от реализации: golden/spec, системная CLI/API, приватный сервис с
записанным журналом либо независимо рассчитанное значение. Для каждого набора указать, что oracle
проверяет и чего не доказывает. Если генератор создаёт ожидаемые данные, его вход, версия/runtime,
команда и провенанс входят в ТЗ; генератор и выход включаются в матрицу. Два запуска должны дать
одинаковые хеши. Не считать генератор и продукт независимыми oracle, если они используют одну и ту
же логику/таблицы.

Мутационный набор выводится из рисков, а не из желаемого процента: условие удалено/инвертировано,
граница сдвинута, поле/байт/порядок изменены, ошибка проигнорирована, cleanup отключён, лимит снят,
состояние дублировано. Связать каждый мутант с test ID и контрактом. `KILLED` требует зелёного
baseline без запрещённых skips и падения ожидаемого теста; compile error, timeout, harness error,
skip и отсутствие ожидаемого теста — `INCONCLUSIVE`. Эквивалентные мутанты документировать отдельно.
Catch rate не заменяет анализ survivors, качества oracle и непокрытых рисков.

В средовых тестах классифицировать skips по ID/причине. Явный live-флаг при ошибке среды должен
падать, если тест заявляет проверку live-контракта; обычный запуск может skip-ать с точной причиной.
Не обнаруживать skips подстрочными эвристиками. Для shared state, fd/daemon/таймеров и RSS-тестов
проверять уникальность ресурса/изоляцию либо сериализовать тесты; повторять рискованный сценарий с
высоким `test-threads` и приводить число повторов.

Уроки из волн: RW-30 показал ложное `KILLED` при скрытом `SKIP`; RW-31 — хрупкий mutation anchor и
устаревшие md5 после fmt; RW-33 — непротестированные бинарный NUL, область schema-match и тихий
live-skip; RW-34 — тест границы через production-константу, эвристика skip и генератор вне матрицы;
RW-35 — флак от общего fd-счётчика и пропущенные дубликат индекса/лишний fd/лимит. Соответствующие
обязательные проверки теперь описаны в `PROCESS.md` §3.4/§4.2/§4.3.

## 4. Протокол red-first (для репозитория Rust-клиента)

1. Задача из `PLAN.md` → тест(ы) из §3 пишутся **первыми** и запускаются: фиксируется падение
   (`cargo test имя -- --exact` + вывод).
2. Минимальная реализация до зелёного; без «зеленения» тестов правкой тестов.
3. Красный/зелёный прогон сохраняются в отчёт задачи (как в `AGENTS.md` этого репозитория).
4. Флаки не замалчиваются: повтор с сохранением обоих результатов.

## 5. Санитизация и приватность в тестах

- Фикстуры уже очищены: токены `analytics_token`/`qos_token`/`user_settings_proto` и тела
  settings-proto заменены placeholder'ами (см. `../re/README.md`).
- Публичные IP клиента в отчётах — `<PUB_IP>`; в тестах используются только адреса Discord.
- Живой аккаунт не участвует в CI; L4 — вне репозитория.
- Скан `T-SEC-02`/`T-SEC-03` обязателен в CI до публикации артефактов.
