### Ниты (предложенные red-тесты — добавляет координатор, ревьюер тестов не добавлял)

- **N1 (P3, покрытие).** Нет теста на `route_dispatch` с известным именем в другом регистре: контракт
  требует точного совпадения (raw + сохранённое имя), но ни U2 (проверяет только `from_name`), ни L1/L2
  (все `t` — верхний регистр) это не пиннят → мутант **m** выжил. Red-тест: `{op:0, t:Atom("ready"), s:1,
  d:Map([])}` (и `Str("ready")`) → `Some`, `kind == None`, `name == "ready"`; плюс, например, `"Ready"`.
- **N2 (P3, покрытие).** P2 проверяет у `take_events` только длину и пустоту — порядок не пиннится →
  мутант **q** выжил (`events()` порядок пинится P1, `take_events` — нет). Red-тест: расширить P2 —
  имена `take_events()` == `["READY","MESSAGE_CREATE","FUTURE_EVENT_X"]`.
- **N3 (P3, опционально).** `s: Atom("nil")` (поле есть, значение не Int) → `seq == None` контрактно, но
  покрыто лишь косвенно через тип-гейт `as_int`; отдельного выжившего мутанта нет. Можно добавить
  под-кейс в U6 для контрактной полноты («"nil" → None»).
- **N4 (P3, дизайн, не дефект).** Встроенный цикл `connect_and_run_resume` не дренирует `events`:
  в долгой сессии буфер растёт линейно (особенно на потоке `GUILD_MEMBER_LIST_UPDATE` — 1048 событий в
  union, payload не парсится). Это осознанный контракт ТЗ §1.3 («вызывающий обязан дренировать»),
  документировано в поле и методах; интеграционный дренаж — вопрос следующей волны/вызывающего.
