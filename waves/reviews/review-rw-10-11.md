## 2. P1 — неограниченный буфер chunked

`exchange` собирает chunked-ответ в `body_bytes` и вызывает `decode_chunked` заново после
каждого `read_more`:

```rust
// transport.rs:373-390
let mut body_bytes = buffer[consumed..].to_vec();
loop {
    match http1::decode_chunked(&body_bytes, max_body) {
        ...
        ChunkedParse::Incomplete => {
            if read_more(&mut stream, &mut body_bytes).await? == 0 { ... }
        }
    }
}
```

`decode_chunked` возвращает `Incomplete`, если в буфере нет `\r\n` (строка размера) или нет
пустой строки после трейлеров:

```rust
// http1.rs:205-236
let Some(line_end) = find_subslice(&bytes[position..], b"\r\n") ... else {
    return Ok(ChunkedParse::Incomplete);
};
...
if size == 0 {
    loop {
        let Some(end) = find_subslice(&bytes[position..], b"\r\n") ... else {
            return Ok(ChunkedParse::Incomplete);
        };
        ...
    }
}
```

`max_body` проверяется только для уже объявленного размера chunk и для распакованных данных
(`http1.rs:239-242`). Следствия:

1. Сервер отправляет `0\r\n` и затем произвольный поток без `\r\n\r\n` — клиент бесконечно
   дописывает `body_bytes` и никогда не возвращает ошибку.
2. Сервер отправляет строку размера без CRLF (например, мегабайты hex-цифр) — то же самое.
3. Трейлеры не имеют ни количественного, ни байтового лимита.
4. Read-timeout отсутствует (P2-2), поэтому зависание не ограничено даже сетевым таймаутом.

Это DoS со стороны сервера/компрометированного CDN, а не «обычный» вход Discord, поэтому P1,
не P0. Но для публичного транспорта лимит обязателен: `max_body_bytes` должен ограничивать
**весь** wire-буфер, а не только полезную нагрузку.

**Минимальная правка.** Ввести `max_wire_bytes` (отдельное поле конфигурации, например 32 МиБ
при `max_body` 8 МиБ; либо `max_body*8 + 64 КиБ` — с запасом на худший случай chunked из
однобайтовых чанков) и проверять его в `exchange` перед каждым `read_more`; в
`decode_chunked` ограничить длину строки размера (1 КиБ) и суммарный блок трейлеров (8 КиБ).
При превышении — `HttpError::TooLarge`/`Http1Error::MalformedChunk`, а не `Incomplete`.
Альтернатива — передать wire-лимит в `decode_chunked` третьим аргументом, но это меняет
публичную сигнатуру и все тесты; предпочтительнее проверка в транспорте + внутренние константы
декодера.

**Red-first.** В `rest_http1.rs`:
- буфер из 2000 нулей + `\r\n\r\n` → сейчас `Complete` (размер 0, длинная строка размера
  проходит); после лимита строки — `MalformedChunk`.
- `decode_chunked(b"0\r\nX: y\r\n", ...)` → сейчас `Incomplete`; после лимита трейлеров
  (или при отсутствии завершающей пустой строки сверх лимита) — ошибка.
В `rest_transport.rs`: стаб отдаёт `HTTP/1.1 200 OK\r\nTransfer-Encoding: chunked\r\n\r\n0\r\n`
и затем бесконечные байты без CRLF; тест под `timeout(1 с)` ожидает `Err(Protocol/TooLarge)`;
сейчас внешний timeout — red.

## 3. P2 — фрейминг и таймауты

### 3.1. TE+CL и порядок transfer-coding

RFC 9112 §6.1/§6.3: отправитель не должен слать `Content-Length` вместе с
`Transfer-Encoding`; получатель, увидев оба, должен рассматривать это как ошибку
(потенциальный request smuggling). Сейчас:

```rust
// http1.rs:105-116
let chunked = headers.iter()
    .filter(|(key, _)| key.eq_ignore_ascii_case("transfer-encoding"))
    .flat_map(|(_, value)| value.split(','))
    .any(|token| token.trim().eq_ignore_ascii_case("chunked"));

if chunked && content_length(headers)?.is_some() {
    return Err(Http1Error::ConflictingFraming);
}
Ok(chunked)
```

- `Transfer-Encoding: gzip` + `Content-Length: 5` → `Ok(false)`, транспорт читает 5 байт как
  тело, хотя это gzip-поток (или иная кодировка). Тихая порча тела.
- `Transfer-Encoding: chunked, gzip` → `Ok(true)`, декодируется только chunked, gzip
  игнорируется; по RFC chunked должен быть последним, а gzip после него — отдельный слой.
- `encode_request` (`http1.rs:284-307`) при непустом теле и отсутствии CL добавляет
  `Content-Length`, даже если вызывающий уже передал `Transfer-Encoding: chunked`. Получается
  запрос с TE+CL и телом без chunk-рамки — ровно smuggling-конфликт (пусть и на клиенте,
  который не является прокси).

**Минимальная правка.** Собрать все TE-токены; если TE присутствует и CL присутствует —
`ConflictingFraming` независимо от значения TE. Разрешить только `["chunked"]`
(регистронезависимо); `["gzip", "chunked"]` — либо реализовать gzip-декодер, либо отвергать
`Unsupported`/`MalformedHead`. В `encode_request` отвергать любое `Transfer-Encoding`:
кодировщик не умеет chunked, поэтому единственный поддерживаемый framing — CL. Обновить
doc-комментарий `ConflictingFraming` («CL и любое TE»).

**Red-first.** Три unit-кейса:
1. `is_chunked([("Transfer-Encoding","gzip"), ("Content-Length","5")])` → `Err(ConflictingFraming)`
   (сейчас `Ok(false)`).
2. `is_chunked([("Transfer-Encoding","chunked, gzip")])` → `Err(...)` (сейчас `Ok(true)`).
3. `encode_request(Post, "/", [("Transfer-Encoding","chunked")], b"x")` → `Err(...)`
   (сейчас `Ok` с добавленным CL).
Плюс transport-кейс: ответ `TE: gzip` + `CL: 2` → `Protocol`, а не 200 с двумя байтами.

### 3.2. DNS/read/write-таймауты

`connect_tcp` ограничивает только `TcpStream::connect`, но не `lookup_host`:

```rust
// transport.rs:285-288
let addresses: Vec<_> = tokio::net::lookup_host((endpoint.host.as_str(), endpoint.port))
    .await
    .map_err(...)?
    .collect();
```

`exchange` пишет и читает без таймаутов:

```rust
// transport.rs:340-347
stream.write_all(request).await...;
stream.flush().await...;
...
// transport.rs:431-443
let read = stream.read(&mut chunk).await...;
```

Последствия: системный resolver может зависнуть; сервер может не читать запрос (переполнение
TCP-буфера и вечный `write_all`); сервер может принять запрос и молчать (вечный `read`).
RW-12 `client.rs` оборачивает `send_with` в `attempt_timeout` (30 с), поэтому высокоуровневый
клиент не зависнет навсегда, но:
- публичные `send`/`send_with` из `transport` остаются без контракта таймаута;
- DNS-фаза внутри `send_with` тоже попадает под 30 с только потому, что снаружи стоит
  `timeout`; сам transport этого не гарантирует;
- при явном `Connection: keep-alive` и ответе без CL/TE `exchange` читает до EOF, то есть до
  закрытия соединения, которого может не быть.

**Минимальная правка.** Добавить в `HttpClientConfig` поля `read_timeout` и `write_timeout`
(разумные дефолты, например 30 с), обернуть `lookup_host` в `tokio::time::timeout` с
`connect_timeout`, обернуть `write_all`, `flush` и каждый `read`; добавить
`HttpError::Timeout(String)`. Для `Connection: keep-alive` либо документировать, что транспорт
не поддерживает keep-alive и всегда закрывает соединение (и не позволять вызывающему
переопределить `Connection`), либо реализовать чтение по framing до конца тела. В рамках
текущего дизайна достаточно второго: не переопределять явный `Connection`, но гарантировать
таймаут чтения.

**Red-first.** Стаб: принимает соединение, читает запрос, не отвечает. `send_with` с
`read_timeout=100 мс` → `Err(HttpError::Timeout)`. Сначала поле `read_timeout` добавляется в
`HttpClientConfig` (red по компиляции теста), затем тест: без реализации таймаута `send_with`
не завершится, внешний `timeout(1 с)` зафиксирует red. Для write-timeout нужен стаб, который не
читает, и маленький `SO_RCVBUF`; тест может быть нестабильным, поэтому допустим отдельный
`#[ignore]`/интеграционный кейс с пометкой.

## 4. P3 — ниты

### 4.1. Явные `Host`/`Connection` не покрыты тестом

ТЗ RW-10, кейс 13: «без `Host`/`Connection` клиент добавляет …; с явными — не дублирует».
`tests/rest_transport.rs:176-212` проверяет только первый сценарий. Код `has_header`
(`transport.rs:273-278`) корректен, поэтому это пробел покрытия, а не баг. Тест:
`HttpRequest::new(Get, "/x").header("Host", "example.test").header("Connection", "close")`,
затем `matches("Host:").count() == 1` и `matches("Connection:").count() == 1`.

### 4.2. Строгость chunked

- `usize::from_str_radix("+5", 16)` возвращает `5`; RFC 9112 §7.1 требует `1*HEXDIG`, знак
  недопустим. Аналогично `"-5"` отвергается, `" 5"` отвергается, но `"+5"` — нет.
- Трейлеры (`http1.rs:222-236`) вообще не валидируются как поля: строка ` X: y` (obs-fold),
  `мусор` без двоеточия и произвольные строки проходят; значения с CR/LF просто делятся на
  новые строки и тоже принимаются. Для ответа Discord это не критично, но парсер должен либо
  валидировать поля, либо отвергать трейлеры.
- Расширения chunk (`;foo=bar`) отбрасываются без проверки; для framing это допустимо, но
  стоит ограничить длину расширения тем же лимитом строки.

Red-first: кейсы `+5`, ` 5`, `5 `, трейлер ` X: y`, трейлер без двоеточия.

### 4.3. JSON-сканер rate-limit

`json_value_start` (`rate_limit.rs:74-115`) не отслеживает глубину: `retry_after` внутри
`{"error":{"retry_after":5}}` будет найден. Для плоских тел Discord это не проявляется, но
контракт в doc-комментарии говорит «поля верхнего уровня». `json_bool`
(`rate_limit.rs:129-139`) проверяет только префикс: `"global":truex` → `true`. Это может
дать ложный `global:true` и лишнюю паузу, но не пропуск retry.

Red-first: вложенный объект → `retry_after` не извлекается (или явно документировать, что
сканер не top-level); `truex` → `global:false`. Правка: счётчик глубины и проверка
разделителя после литерала.

### 4.4. Нормализация telemetry-пути

`first_path_segment` (`telemetry.rs:23-42`) режет по первому `?`/`#` и первому `/`, но не
нормализует `.`/`..`, повторные `/` и percent-encoding. Примеры, которые сейчас проходят:
`/./science`, `/foo/../science`, `//science`, `/%73cience`, `/science%2Fevents`. Первые три
могут быть нормализованы сервером до `/science`; последние два — тоже, если сервер декодирует
`%2F`/`%73`. ТЗ сознательно разрешает `/science%2Ffoo` (кейс 2), поэтому это остаточный риск,
а не нарушение замороженного контракта. Рекомендация: нормализовать путь до сравнения
(percent-decode, удаление dot-segments, схлопывание `//`) и пересмотреть кейс 2 ТЗ; до этого
не вызывать `guard_target` после какой-либо нормализации.

### 4.5. `httparse` не используется

`rg httparse rust/` находит только `rust/Cargo.toml:28` и
`rust/crates/discord-core/Cargo.toml:14`. Зависимость разрешена и лежит в lock, но мёртвая.

## 9. Остаточные риски (после закрытия P1/P2)

- TLS: доверие `webpki-roots` (снимок крейта), без pinning; DNS не пиннится (TOCTOU/rebinding
  вне модели угроз локального клиента). Для Discord это приемлемо.
- Нет keep-alive/пула, HTTP/2, прокси, сжатия; клиент не просит `Accept-Encoding`. По дизайну
  варианта A.
- 1xx interim-ответы не обрабатываются отдельно; `Expect: 100-continue` не отправляется,
  поэтому на практике не проявляется.
- `Retry-After` как HTTP-date не парсится (только секунды); Discord шлёт секунды.
- 204/304 возвращаются без тела независимо от полей; для этих статусов корректно.
- `Connection: keep-alive`, переданный явно, вместе с ответом без CL/TE может дать чтение до
  EOF; закрывается таймаутом из P2-2, но семантику keep-alive транспорт не поддерживает.
- Telemetry: обход через нормализацию пути (§4.4); после интеграции `guard_target` в RW-12
  проверяется сырой target — инвариант нужно сохранить.
- Rate-limit: вложенные поля/`truex` (§4.3); на плоских телах Discord не проявляется.
- `httparse` — мёртвая зависимость (§4.5).

## 10. Условия приёмки

1. **До любой живой интеграции REST** закрыть P1-1 (wire-лимит chunked) и P2-1 (TE+CL).
2. **До живой интеграции желательно** закрыть P2-2 (DNS/read/write-таймауты) или явно
   зафиксировать, что единственный путь — через RW-12-фасад с `attempt_timeout`; для публичного
   `transport` это плохой контракт.
3. P3 можно закрывать отдельной волной/нитами; P3-1 (явные заголовки) и P3-2 (`+5`/трейлеры)
   дешёвы и хорошо ложатся в текущие тесты.
4. Каждая правка — red-first: сначала тест/лог падения, затем минимальный код; не «зеленить»
   тесты под реализацию.
5. После правок повторить три обязательных прогона и приложить red/green-логи в
   `waves/<ID>/reports/`.

**Итог:** код RW-10/RW-11 в текущем виде пригоден для локальных стабов и интеграции за
RW-12-фасадом, но P1/P2 нужно закрыть перед реальным REST. P0-блокеров нет; вердикт —
**принято с нитами**.
