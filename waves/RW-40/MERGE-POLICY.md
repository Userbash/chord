# MERGE-POLICY — окно слияния, готовность и возврат на доработку

Дата: 2026-10-24. PM. Дополняет `PROCESS.md` §3.5–3.8, `TEST-POLICY.md`,
`PARALLEL-LANES.md`. Источник истины по процессу — `PROCESS.md`; этот файл фиксирует
правила слияния для параллельных линий RW-40.

## 1. Что считается «окном слияния»

**Окно слияния — не календарное время, а граница batch/вертикального среза.**

- Кодовые линии (G1/G2) работают параллельно в своих файлах.
- Слияние в integration-поток — когда срез **готов**, а не «в 18:00».
- Один merge-цикл на batch (3–6 карточек) или на законченный vertical slice.
- В момент merge: **один** integration-исполнитель, **один** `cargo` на target-dir.
- Нельзя сливать в середине red-фазы, при незакрытом P0/P1 или при незамороженном контракте.
- Hotfix P0 — отдельное окно, но с теми же гейтами.
- Live-окно (READY/send/voice) — **отдельно** от code-merge, 1 окно на приёмку.

## 2. Готовность к слиянию (Definition of Ready)

Владелец линии сдаёт **handoff**:

| Пункт | Требование |
|---|---|
| Контракт | заморожен: IPC args/result, typed errors, `[L]/[S]/[D]` |
| Тесты | red-лог, green-лог, targeted; новые/изменённые тесты не ослаблены |
| Код | clippy `-D warnings`, fmt, tsc; нет секретов в логах |
| Evidence | md5 файлов, команды прогонов, known gaps |
| Границы | только свои файлы; чужие не тронуты |
| Live | если функция live — E3; иначе явно `live unverified` |
| UI | loading/empty/error/disabled, aria/focus, без мёртвых кнопок |
| Документы | обновлены только после accepted, не в red |

**Не готов к merge**, если:

- есть P0/P1 без фикса;
- тест изменён «под код» или удалён assert;
- контракт придуман (`[M]/[A]` вместо `[L]/[S]/[D]`);
- `gate` красный;
- e2e skip выдан за pass;
- есть незакрытый конфликт интерфейса.

## 3. Полный цикл слияния

```
handoff
  → независимый review (не автор)
  → batch gate: fmt/clippy/core/workspace/gate:worker
  → G6 parity: evidence/levels
  → PM accept
  → docs/journal
  → merge в integration
```

Только после этого задача считается **accepted**.

## 4. Возврат на доработку

Да, код **возвращается**, пока не пройден полный цикл:

| Причина | Действие |
|---|---|
| P0/P1 | **return**, merge запрещён, тот же card |
| gate/clippy/fmt/tsc fail | **return** с логом и repro |
| тест ослаблен/удалён | **P0 return**, восстановить проверку |
| контракт не подтверждён | **return** в RE, не «догадаться» |
| конфликт файлов/интерфейса | PM/ADR, затем **return** |
| P2 | можно `deferred` с тикетом, если не блокирует срез |
| P3 | backlog, не тормозит merge |

Правила цикла:

1. Возврат — это **та же карточка**, статус `returned`, не новая задача.
2. Автор исправляет только свои файлы; reviewer не автор.
3. После фикса: targeted → batch gate → review → G6 → accept.
4. **2 одинаковых отказа** → смена подхода (LOOP-LEDGER).
5. **3-я идентичная попытка запрещена**; нужна декомпозиция/ADR.
6. Нельзя «принять с красным» или «перенести P1 в P2» без письменного waiver PM.
7. Пока P0/P1 не закрыты, срез не попадает в `gate:release`.

## 5. Кто принимает решение

| Роль | Решение |
|---|---|
| PM | final accept, окно, waiver только письменно |
| G6 | parity-ok/deferred; блокирует `[A]`-функции |
| G4 | gate/verdict; skip ≠ pass |
| Reviewer | независимое code review; не автор |
| Author | фикс после return |

## 6. Конфликты и слияние

- Общие файлы (`state/types.rs`, `state/reducer.rs`, `TASKS`, `PLAN`, `STATUS`, `ROADMAP`)
  правит PM/Team Lead, не воркеры.
- При конфликте контракта — **ADR**, затем обе линии перезапускают targeted.
- Нельзя «подогнать» одну сторону под другую без теста.
- После merge — `gate:release`; перед выкладкой — `gate:qualify`.

## 8. Запреты

- merge в red-фазе;
- merge без targeted/gate;
- принимать source-scrape как единственный oracle;
- выдавать `[M]/[A]` за реализованную функцию;
- ослаблять тест, чтобы пройти gate;
- параллельный `cargo` на одном target-dir;
- коммит/пуш от PM (только координатор).
