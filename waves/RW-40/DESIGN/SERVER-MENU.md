## 1. Что является источником истины

| Слой | Источник | Статус | Что запрещено |
|-|-|-|-|
| Список серверов | `READY.guilds[]` + `READY_SUPPLEMENTAL`; REST-ручки списка **нет** (`GET /users/@me/guilds` отсутствует в бандле) | `[S]`/`[L]` | досоздавать гильдии в UI, «демо-серверы» в проде |
| Preview инвайта | `GET /invites/{code}` (+`with_counts`, `with_expiration`, …) | `[S]`; live не наблюдался, коды `[A]` | придумывать данные preview без ответа |
| Join по инвайту | `POST /invites/{code}`, тело `{session_id, invite_instance_id, received_installation_id}`; ответ — invite-объект (`guild_id`, `target_channel_id`, `target_message_id`) | `[S]`; HTTP-коды/TTL/ошибки `[A]` | считать успехом не-2xx; придумывать поля |
| Перейти в сервер (preview/lurker) | `PUT /guilds/{id}/members/@me?lurker=true`, тело `{}`, ответ **204** | `[L]` | смешивать с accept-invite; ждать тело ответа |
| Leave | `DELETE /users/@me/guilds/{id}`, тело `{lurking: boolean}`; ответ **не читается** | `[S]`; коды и семантика lurker/guest `[A]` | собирать тело в UI; считать «тихий выход» успехом без 2xx |
| Создать инвайт | `POST /channels/{id}/invites` | `[S]`; live/коды `[A]` | показывать фальшивую ссылку |
| Список инвайтов | `GET /guilds/{id}/invites`, `GET /channels/{id}/invites` | `[S]`; live/коды `[A]` | — |
| Capabilities | ответ backend (`canInvite`, `isOwner`, `canManage`), не вычисление по ролям на клиенте | `[A]` | угадывать право по названию роли |
| Ошибки | HTTP-статус + машинный `code` от backend | коды invite-flow `[A]` | парсить текст ошибки для логики |

UI **никогда** не строит URL, тело запроса и не выбирает endpoint. Он вызывает сервис
(`resolveInvite(code)`, `acceptInvite(code)`, `enterGuild(id, {lurker})`, `leaveGuild(id)`,
`createInvite(guildId)`) и рисует результат. `confirmed` из `rest-static.json` не читается
и не является условием успеха (см. §0).

## 2. Поток

### 2.1 Данные, которые нужны экрану

```text
Guild       { id, name, iconUrl?, isOwner, canInvite, canManage, position }
GuildList   { state: loading|ready|empty|error|offline, items: Guild[], error? }
InvitePreview { code, guildId, guildName, iconUrl?, memberCount?, presenceCount?,
                expiresAt?, inviter?, channelId? }
JoinResult  { state: idle|resolving|preview_ready|accepting|accepted|error|null,
              preview?: InvitePreview, guildId?: string, error?: string }
EnterResult { state: idle|entering|entered|error, guildId, lurker: true, error?: string }
LeaveResult { state: idle|pending|left|error, guildId, error?: string }
InviteInfo  { code, url?, expiresAt?, uses?, canCreate }
```

`JoinResult` и `EnterResult` — **разные** состояния: первый про принятие инвайта
(`POST /invites/{code}` `[S]`), второй про вход в сервер/предпросмотр
(`PUT /guilds/{id}/members/@me?lurker=true` `[L]`). Их нельзя склеивать в один «успех»:
у них разные запросы, коды и последствия.

`iconUrl` — только если backend отдаёт готовый URL; UI не склеивает CDN-адреса. Пока иконок
нет — монограмма 2 буквы, как в существующем `.guild-item` (`[T]`/`[A]`).

Внешняя ссылка (`discord.gg/…`, `discord.com/invite/…`) не открывается браузером: код
извлекается и передаётся в тот же join-поток (когда deep links появятся — N4-03). До этого
пользователь вставляет ссылку в поле вручную.

### 2.3 Join по инвайту

Это **два разных действия** с разными состояниями; смешивать их нельзя.

| Действие | Запрос | Ответ | Статус |
|-|-|-|-|
| A. Принять инвайт | `POST /invites/{code}` | invite-объект (`guild_id`, `target_channel_id`, …) | `[S]`; коды/TTL `[A]` |
| B. Открыть сервер из preview | `PUT /guilds/{id}/members/@me?lurker=true`, тело `{}` | **204**, тела нет | `[L]` |

A добавляет в гильдию; B даёт доступ к просмотру (lurker) и не заменяет A. В N1-02 основная
кнопка — A; B — отдельное действие на preview-карточке и вход для N1-03.

```text
[idle] --«+»--> [dialog: idle]
[idle] --submit(валидный код)--> [resolving] --2xx + invite--> [preview_ready]
                                      |--4xx/5xx/network--> [error] --«Повторить»--> [resolving]
[preview_ready] --«Присоединиться»--> [accepting] --2xx + guild_id--> [accepted]
                                      |--403 banned/screening/...--> [error] (без повтора)
                                      |--timeout/unknown--> [error: результат неизвестен]
[preview_ready] --«Открыть сервер»--> [entering] --204--> [entered]  (lurker, отдельный stream)
[accepted] --закрыть--> [rail обновлён] (когда гильдия есть в READY/локальном списке)
```

Шаги:

1. **Открытие.** Фокус в поле `#join-invite-input`; заголовок «Присоединиться к серверу»;
   кнопка «Присоединиться» disabled, пока поле пустое.
2. **Ввод/нормализация.** Принимается ссылка или код: trim, убрать завершающий `/`, из
   `…/invite/<code>` и `…/<code>` взять последний сегмент, разрешить `[A-Za-z0-9-]` длиной
   2…32. Чистая функция, тестируется без DOM.
3. **Preview.** `GET /invites/{code}` с `with_counts`/`with_expiration` `[S]`; live не
   наблюдался, поэтому коды ошибок — `[A]`. Пока ответа нет — skeleton; данных не выдумывать.
   Если backend ещё не отдаёт resolve, preview-local (чип с кодом) остаётся, а карточка скрыта.
4. **Accept.** Один вызов `acceptInvite(code)`. На время запроса `aria-busy="true"`, обе
   кнопки disabled, повторный клик игнорируется, статус «Приглашение обрабатывается» `[D]`.
5. **Успех A.** Только 2xx от `POST /invites/{code}` `[S]`. Диалог закрывается, live-статус
   «Вы присоединились к серверу «{name}»!» `[D]`. В ответе есть `guild_id` `[S]`; имя/иконка
   берутся из `READY`/локального списка, иначе плитка `data-state="pending"` (`aria-busy`) —
   это не «успех». `GUILD_CREATE` в 7 живых сессиях не наблюдался `[S]`/`[A]`, поэтому не
   строить на нём единственный путь обновления.
6. **Успех B.** Только **204** от `PUT …?lurker=true` `[L]`. Это отдельный статус
   «Сервер открыт для просмотра» `[A]`; он **не** означает членство и не закрывает accept-поток.
7. **Ошибка.** Диалог остаётся открытым, код сохранён, фокус на поле/кнопке повтора,
   текст в `#join-error[role="alert"]` (§3.1). Повтор повторяет **только упавший шаг**:
   если accept уже вернул 2xx, повторный accept не отправляется.

### 2.4 Выход с сервера

```text
[menu] --«Покинуть сервер»--> [confirm: idle]
[confirm] --«Покинуть сервер»--> [confirm: submitting] --2xx--> [closed] --rail обновлён + статус
                                            |--ошибка--> [confirm: error] --«Повторить»--> [submitting]
[confirm] --«Отмена»/Esc/клик вне--> [closed], фокус на пункт меню
```

1. Confirm — `role="alertdialog"`, заголовок «Вы уверены, что хотите покинуть этот сервер?»
   `[D]`, текст о последствиях (если сервер единственный — «Вы покинете сервер и вернётесь
   к личным сообщениям» `[A]`).
2. Кнопка подтверждения — destructive «Покинуть сервер» `[D]`; кнопка отмены — «Отмена» `[D]`.
3. Клиент отправляет `DELETE /users/@me/guilds/{id}` с телом `{lurking: boolean}` `[S]`.
   `lurking` вычисляется клиентом (`isLurking || isGuest`); точная семантика lurker/guest
   и коды ответа — `[A]` (NETWORK-CONTRACTS §1.3).
4. На время запроса обе кнопки disabled, `aria-busy`, Esc не закрывает.
5. Успех — только 2xx (тело ответа **не читается** `[S]`): удалить `.guild-item` из рейла,
   выбрать предыдущую гильдию (или экран ЛС), статус «Вы покинули сервер» `[D]`.
6. Ошибка/таймаут — диалог открыт, гильдия остаётся в рейле, текст ошибки, «Повторить» (§3.2).
   При таймауте результат неизвестен: UI не удаляет плитку до 2xx.
7. Владелец сервера: «Покинуть сервер» недоступен (`aria-disabled="true"` + пояснение
   «Владелец сервера» `[D]`); вместо выхода — «Удалить сервер» `[D]` (`POST /guilds/{id}/delete`
   `[S]`), но удаление в N1-02 **не реализуется** и показывается disabled.

### 2.5 Инвайт (создание/копирование ссылки)

Поток отделён от join: он про **приглашение людей на текущий сервер**.

```text
[menu «Пригласить на сервер»] --> capability.canInvite?
   нет --> пункт aria-disabled, клик — no-op (как inbox/gift)
   да  --> [invite-dialog: loading] --> ready | empty | error
ready: ссылка + «Скопировать ссылку-приглашение» + срок действия
```

- `loading` — skeleton строки ссылки, `aria-busy`;
- `ready` — readonly-поле `#invite-link` + кнопка копирования; успех копирования —
  «Приглашение скопировано!» `[D]`; ошибка clipboard — «Не удалось скопировать ссылку» `[A]`;
- `empty` — ссылки нет: «Создать ссылку-приглашение» `[D]` (`POST /channels/{id}/invites`
  `[S]`; live не наблюдался, коды `[A]`);
- `error` — «Не удалось создать ссылку-приглашение.» `[D]` + «Повторить» `[D]`;
- `capability=false` — пункт меню `aria-disabled`, диалог не открывается.
  Это ограничение прав, а не отсутствие контракта: контракт есть `[S]`, live-проверка — `[A]`.

## 3. Состояния и ошибки

Правило: статус — источник истины, текст ошибки — только для человека. Один и тот же
HTTP-код может значить разное; поэтому семантические случаи различаются **машинным кодом**,
который обязан отдать N1-01. Все семантические коды в таблицах помечены `[A]` — это
**требование к контракту**, а не утверждение, что они уже есть в дампе.

### 3.1 Join

Статус успеха — только **2xx**. Поле `confirmed` не используется. Коды invite-flow, кроме
явно помеченных `[S]`, не наблюдались live и являются требованием к N1-01 (`[A]`).

| Шаг | Случай | Условие | Заголовок / текст | Кнопки | Метка |
|-|-|-|-|-|-|
| input | Пусто | клиент | поле `aria-invalid="true"`, «Введите код приглашения...» как placeholder `[D]`, текст «Введите ссылку-приглашение или код» `[A]` | «Присоединиться» disabled | `[A]` |
| input | Формат | клиент | «Ссылка-приглашение выглядит неверно» `[A]` | правка поля | `[A]` |
| both | 401 | сессия | «Сессия истекла. Войдите снова.» `[A]`; диалог закрыть, код не сохранять | auth-gate | `[A]` |
| both | 403 generic | нет прав | «Недостаточно прав, чтобы присоединиться к этому серверу.» `[A]` | «Повторить» `[D]` | `[A]` |
| both | 403 banned | клиент ловит `USER_BANNED` | «Ой-ой. Похоже, вас забанили. Теперь вы не сможете присоединиться к этому серверу и взаимодействовать с ним.» `[D]` | только «Закрыть» `[D]` | `[S]` (код) / `[A]` (HTTP-статус) / `[D]` (текст) |

### 3.5 2xx — единственный критерий успеха

Поле `confirmed` из `rest-static.json` — артефакт схемы (false у всех 904 записей), а не
оценка результата (`NETWORK-CONTRACTS.md` §0.3). Поэтому:

- «успех» = **только 2xx** от соответствующего запроса: `POST /invites/{code}` (2xx; 200 —
  ожидание `[A]`, тело — invite object `[S]`); `PUT /guilds/{id}/members/@me?lurker=true` (**204**, тела нет) `[L]`;
  `DELETE /users/@me/guilds/{id}` (2xx, тело не читается) `[S]`;
- локальное намерение, optimistic-переход и «сервер, наверное, ответил» успехом не считаются;
- таймаут/обрыв = состояние «результат неизвестен» (§3.1/§3.2), рейл не мутируется;
- 2xx accept без данных гильдии → плитка `data-state="pending"`, success-текст только когда
  имя гильдии известно (из ответа или `READY`);
- отдельного «гейта на подтверждение» нет: контракт accept-invite `[S]`, live-проверка —
  отдельная задача окна `[A]`.

## 8. Что нельзя

1. **Не выдумывать endpoint.** В UI допустимы: `GET /invites/{code}` `[S]`,
   `POST /invites/{code}` `[S]`, `PUT /guilds/{id}/members/@me?lurker=true` `[L]`,
   `DELETE /users/@me/guilds/{id}` `[S]`, `GET/POST` инвайтов `[S]`, `GET /guilds/{id}` `[D]`.
   Список серверов — только `READY`/`READY_SUPPLEMENTAL` (REST-ручки нет `[S]`). Никаких
   «refresh»-эндпоинтов и догадок; неизвестное — disabled/ошибка, а не «попробуем».
2. **Успех — только 2xx.** Никакого `confirmed`-поля: в `rest-static.json` оно стоит в
   `false` у всех 904 записей и ничего не значит (`NETWORK-CONTRACTS` §0.3).
   Локальное намерение, optimistic-переход и таймаут успехом не являются.
3. **Никакого оптимистичного выхода.** Плитка удаляется только после 2xx от
   `DELETE /users/@me/guilds/{id}`. Иначе при ошибке пользователь «теряет» сервер визуально,
   хотя остался в нём.
4. **Не смешивать accept-invite и enter-guild.** `POST /invites/{code}` (200, членство) и
   `PUT /guilds/{id}/members/@me?lurker=true` (204, просмотр) — разные действия, состояния
   и тексты; успех одного не выдаётся за другой.
5. **Не показывать имя/иконку/участников сервера до ответа `GET /invites`.** Клиентский
   preview — только нормализованный код. Иначе это ложные данные и утечка ожиданий.
6. **Не логировать код приглашения.** В логах — только хвост (последние 4 символа) или хэш;
   код не попадает в analytics/ошибки.
7. **Не парсить текст ошибки.** Логика — по статусу + машинному коду; текст меняется.
8. **Не глотать ошибки.** Любой отказ = видимый текст + повтор упавшего шага (кроме
   необратимых: бан, владелец, устаревший клиент).
9. **Не блокировать UI навсегда.** Таймаут 15 с обязателен; иначе «вечный» pending.
10. **Не копировать ассеты.** Ни PNG, ни иконок, ни шрифтов из дампа; только числа и тексты.
11. **Не менять общие файлы.** `index.html`, `actions.js`, CSS — зона G2/интеграции; G3
    отдаёт контракт, а не патч.
