## 3. P1 — блокеры (2)

### P1-1. Кнопка «×» баннера ошибки — лениво созданный `data-action` без обработчика

`data-action="dismiss-picker-error"` в разметке поповера (§2.3, строки 401-404) — новый узел
внутри лениво монтируемого дерева. Механизм отказа тот же, что в закрытом P1-1 из 38B:

- глобальный обработчик `[data-action]` навешивается один раз в `initActions`
  (`actions.js:925-928`; вызов — `app.js:1500`), делегирования и `MutationObserver`
  в модуле нет;
- узел создаётся в `openReactionPicker()` (§5.3, строка 840), то есть **после** инициализации,
  и в `NodeList` не попадает;
- перечень слушателей, навешиваемых при открытии (§5.3, строка 846), содержит только
  `keydown`, `pointerdown`, `input` и клик по `reaction-picker-close`. Для dismiss — ничего;
- при этом §3.2.4 (строка 680 и диаграмма §3.2) рассчитывает на ручное закрытие баннера
  («или закрыт баннер ошибки» ведёт обратно в `ready`), а §8 не содержит ни одного оракула
  на dismiss: N-05 проверяет только текст и таймер.

Итог при буквальной реализации: кнопка «×» не работает — ни своего обработчика, ни глобального,
ни ошибки в консоли (просто no-op). Это нарушает и §0.2 п.7 (новый узел обязан иметь
red-first оракул).

**Что исправить:**
- либо описать прямой обработчик dismiss в `openReactionPicker()` рядом с close
  (и тогда `data-action` можно оставить как маркер, как у `.reaction-add-btn`),
  либо убрать `data-action` и дать атрибут-маркер без глобальной семантики;
- добавить оракул: клик по `.reaction-picker-banner-dismiss` скрывает баннер
  (`hidden === true`), возвращает `data-state="ready"` и **не** закрывает поповер
  и не меняет `data-active-screen`;
- заодно дополнить §5.2: порядок `Tab` внутри поповера при видимом баннере включает
  `.reaction-picker-banner-dismiss` между `.emoji-close-btn` и активной вкладкой —
  сейчас таблица перечисляет 4 стопа и про эту кнопку молчит.

### P1-2. `pending` + выбранная быстрая реакция в тулбаре: 4.04:1 при инварианте ≥ 4.5:1

Нормативный CSS §7.1 задаёт `.msg-toolbar-btn[aria-pressed="true"]` фон `var(--accent-soft)`
и цвет `var(--text-accent)` (строки 1226-1232), а ниже — `.msg-toolbar-btn[data-pending="true"]`
цвет `var(--text-muted)` (строки 1244-1248). Специфичность селекторов равна (0,2,0), правило
pending идёт позже, поэтому в состоянии «нажал быструю реакцию, ждём ответа» побеждает
`--text-muted` на композите `--accent-soft` поверх `--surface-4`, то есть `#96979e` на
`#333651` = **4.04 : 1**.

Состояние достижимо буквально по контракту: `reactionButtons.get(emojiTarget)` передаётся
в `requestReaction` как `element` (`message-toolbar.js:213`), `data-pending` ставится
синхронно до `await invoke` (`reactions.js:176-177`), а `syncPressed` сразу после вызова
выставляет `aria-pressed="true"` из оптимистичного `overrides` (`message-toolbar.js:224-225`,
`reactions.js:147`). То есть оба атрибута живут на одном узле всё время запроса.

Почему это блокер, а не придирка:
- §0.2 п.1 объявляет жёсткий инвариант «контраст текста ≥ 4.5:1», а шапка (строка 15) —
  «100% … контраст текста WCAG 2.2 AA»;
- §7.2.1 содержит строку «Кнопка тулбара, нажатая реакция — 5.74:1», но строки для
  `pending`-состояния кнопки нет, а §3.1 п.6 (строка 581) нормирует только счётчик пилюли
  (5.05:1 на `#28282c`) и для тулбара цифру не даёт;
- комментарий в CSS (строка 1244) утверждает «без opacity — контраст иконки сохраняется»,
  что в паре с `[aria-pressed]` неверно.

Пилюля `.reaction` этот случай проходит: `pending` побеждает правило выбранной, но фон
остаётся `accent-soft` → `#242640`, а `--text-muted` на нём даёт 5.06:1. Ломается только
тулбар.

**Что исправить (минимум):** добавить правило для пересечения состояний, например
`.msg-toolbar-btn[data-pending="true"][aria-pressed="true"] { color: var(--text-accent) }`
(5.74:1 на `#333651`), и строку в §7.2.1 с этой парой. Альтернатива — в `pending` не менять
цвет вообще (оставить цвет состояния `pressed`/`idle`): тогда 5.74 и 4.72 соответственно.

## 4. P2 — точность и поддерживаемость (5)

1. **§2.1/§2.2/§5.1 против §5.3: `aria-controls` ссылается на узел, которого нет.**
   Оба триггера обязаны нести `aria-controls="reaction-picker-popover"` (строки 246, 318, 802),
   а §5.3 (строка 840) и §1.2 (178) требуют, чтобы до открытия этого id в документе не было.
   IDREF не разрешается, и это противоречие внутри нормативной части. Дешёвое решение:
   выставлять/снимать `aria-controls` вместе с `aria-expanded` (то есть только пока поповер
   смонтирован), либо записать это как исключение рядом с двумя существующими в §5.1.

2. **§3.1 п.7 обещает стиль `.reaction-add-btn[aria-disabled="true"]`, которого нет в §7.1.**
   Таблица состояний (строка 582) даёт `opacity: var(--state-disabled-opacity)` и
   `cursor: not-allowed` для пилюли, `:disabled` и `.reaction-add-btn[aria-disabled="true"]`.
   В CSS §7.1 правило есть только для `.reaction:disabled` / `.reaction[aria-disabled="true"]`
   (строки 1089-1093); у `.reaction-add-btn` — только `:hover` и `[aria-expanded]`.
   §7.1.0 объявляет CSS единственным нормативным источником, значит состояние «заблокировано»
   у кнопки «+» не определено. Добавить селектор в существующее правило.

3. **§3.2 использует непрефиксные id в разделе про поповер.** Строка 628 —
   «в сетке `#emoji-grid` есть ≥ 1 эмодзи», строка 649 — «фильтр текущей вкладки `#emoji-tabs`»,
   строка 653 — «Сетка `#emoji-grid` очищается». Раздел §3.2 целиком описывает состояние
   `#reaction-picker-popover`, а §2.3 требует у поповера префиксные id; строка 660 в том же
   абзаце аккуратно пишет `#…-search`. Читатель реализации поповера возьмёт `byId("emoji-grid")`
   и сломает `initEmojiConsole`. Привести к `#reaction-picker-grid` / `#reaction-picker-tabs`
   (или к форме `#…-grid`, как в строке 660).

4. **§8.2, строка 1697: ложное утверждение о покрытии `data-pending`.** «Ни один из узлов
   … `data-pending` не покрыт тестами сегодня (проверено `grep -rl`)» — неверно:
   `data-pending` проверяется в `tests/unit/chat-reactions.test.mjs:372,376`,
   `tests/unit/gui-spike-features.test.mjs:1245,1463,1466`. Не покрыт именно `aria-busy` на
   пилюле — это N-10 и надо сказать только про него, иначе следующая ревизия снова будет
   сверять покрытие по ложной базе.

5. **§5.2, порядок `Tab`.** «Переход `Tab` внутри пикера проходит 4 стопа:
   `#…-search` → `.emoji-close-btn` → активная вкладка → активная ячейка» (строка 814).
   При видимом баннере фокусируемых узлов пять (добавляется `.reaction-picker-banner-dismiss`),
   а `.emoji-preview`/сетка в состоянии `loading` меняют состав. Формулировку стоит сделать
   условной («в состоянии `ready` без баннера — 4 стопа»), иначе это ещё один текст,
   который разойдётся с реализацией. Пересекается с P1-1, но правится отдельной строкой.
