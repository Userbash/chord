## 3. P2 — не блокирует приёмку

### P2-1. Guard зелёный только на композитном дереве; в HEAD он красный на пяти командах

`REPORT.md` §7.1 называет только дельту N-05 (`update_guild_notification_settings`,
`update_channel_notification_override`). Независимый прогон того же парсера против
`git show HEAD:rust/gui-spike/src/main.rs` даёт **пять** недостающих команд:

```
pins_list (app.js:1428)
threads_list (app.js:1434)
create_invite (features/invite-modal.js:370)
update_guild_notification_settings (features/notifications.js:1547)
update_channel_notification_override (features/notifications.js:1606)
```

В рабочем дереве — 49 обработчиков из 23 литеральных `invoke`, недостающих нет. Практический
смысл: если интеграционный мерж возьмёт тест INT-07, но не возьмёт дельты `main.rs` трёх
карточек, `gate:worker` покраснеет — это правильное поведение guard'а, но условие мержа
в отчёте описано уже, чем реальность. Запись об этом — §4.1.

### P2-2. Восстановленный блок 429 и его реализация — тоже чужая незакоммиченная дельта

Блок зелёный только вместе с cooldown'ом в `features/actions.js` (в HEAD `confirmLeave()`
не содержит `leaveCooldown` и `startLeaveCooldown`). Сам блок — документированная правка
`g05-rest` (§5), и INT-07 теперь редактирует те же строки. Текст совпадает с §5 дословно,
расхождений нет, но две карточки правят один хунк: при мерже возможен конфликт, а
ответственность за финальное состояние размывается. Владельца стоит зафиксировать
(`g05-rest`/integration), INT-07 — только сослаться на §5.

### P2-3. Обёртка `settings.showPane` не перехватывает внутренние вызовы `settings.js`

`app.js:1752-1756` подменяет публичное свойство `settings.showPane`. Внутри
`features/settings.js` живёт своя функция `showPane` (строка 769); её вызывают навигация
(842), стартовый переход (915) и ссылка «Уведомления» (579) — мимо обёртки. Сегодня
достижимые пути закрыты: клики по `#settings-nav` дополнительно слушает `app.js:1745-1747`,
а ссылка «Уведомления» — no-op из-за `PANE_BY_SECTION` с русскими ключами. Живого дефекта нет,
но формулировка «после любого программного переключения» в отчёте и комментарии сильнее
реальности. Устойчивый вариант — `MutationObserver` на `#settings[data-active-pane]` в
`app.js` (без правки чужого файла) либо хук в `settings.js` при следующем касании.

### P2-4. Guard видит только литеральные `invoke("…")`

Регулярка `/invoke\(\s*"([A-Za-z0-9_]+)"/g` пропускает вычисляемые имена, шаблонные строки
и вызовы через `__TAURI_INTERNALS__`. Сейчас в UI таких нет (23 литеральных вызова, все
найдены), но новый код может обойти инвариант молча. Дешёвое усиление — отдельная проверка
«в `ui/**/*.js` нет `invoke(` с первым аргументом, не являющимся строковым литералом и не
`invoke`-адаптером».

### P2-5. Второй мета-тест запрещает voice-IPC в `app.js` навсегда

`tests/unit/gui-spike-features.test.mjs:4232-4241` требует, чтобы `app.js` не вызывал
`set_input_device` … `set_ptt_key`. Когда появится карточка wiring'а voice-devices, этот тест
заблокирует корректную работу, пока его не обновят. Стоит записать в ту карточку явный пункт
«снять запрет из INT-07 и перевести секцию из предварительной в рабочую».

### P2-6. RED-артефакты не содержат команды и exit code

`red-pass3.log` и `red-pass3-replay.log` начинаются сразу с вывода тестов; строки
`$ node --test …` и `EXIT=1` в файлах нет (в `green-pass3.log` такие строки есть). Итог
`exit 1` в `REPORT.md` §3 выводится из падений, но по `TEST-POLICY.md` §4 артефакт должен
фиксировать команду и код возврата. Сами логи содержат ровно 5 ожидаемых падений — к
содержанию претензий нет, только к формату.

### P2-7. Записи `DECISIONS.md` остались черновиком

Черновики `D-40-INT-07-01`/`D-40-INT-07-02` в §7 корректны по составу (контекст, решение,
риск) и покрывают оба изменения контракта, включая свёрнутую секцию. Файл — зона Team Lead;
до мержа записи должны быть внесены, иначе `TEST-POLICY.md` §5 формально не выполнен.

### P2-8. Дефолты модалки уведомлений по-прежнему выдаются за факт

`P2-2`/`P2-4` второго ревью не исправлены и в этой матрице не исправимы: проекции
