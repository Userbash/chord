# G6 — RE Parity: отдел сверки с эталонным Discord

Дата создания: 2026-10-24. Владелец процесса: PM (DeepSeek).
Статус: **active**. Отдел создан по требованию владельца: никакой «отсебятины»,
только подтверждённые функции эталона и явно помеченные авторские решения.

## 1. Миссия

G6 отвечает за **паритет** разрабатываемого клиента с эталонным Discord:

1. Найти функцию/поведение в эталоне (REA, dump, live capture).
2. Зафиксировать доказательство (файл, строка, артефакт, capture, tool evidence).
3. Сравнить с текущим приложением.
4. Описать gap, DoD, тест и приоритет.
5. Передать в G1/G2/G3/G5 и проверить результат **до** приёмки PM.

G6 не пишет продуктовый код и не принимает решения «на глаз».

## 4. Evidence-модель (обязательно)

Каждая строка матрицы имеет:

- `source`: `app.asar:<module>`, `re-deep:<file>`, `live:<capture-id>`, `docs/re:<file>`;
- `evidence`: `E0` нет / `E1` статический источник / `E2` E1 + тест / `E3` live;
- `level`: **[L]** live-захват / **[S]** call-site в коде эталона / **[D]** только Enum-запись дампа / **[M]** модель/измерение / **[A]** авторское решение или нет подтверждения;
- `confirmed`: **не использовать поле `confirmed` из `rest-static.json`** (оно `false` у всех 904 записей и не является оценкой достоверности); вместо него — `level` + `source`;
- `app`: `implemented` / `partial` / `absent` / `unknown` / `verified`;
- `gap`, `DoD`, `test`, `owner`, `priority`, `confidence`.

Правила:

1. **E0 → нельзя кодировать.** Сначала RE-задача.
2. `[A]` допустим только для дизайн-значений/приоритетов, **не для существования функции**.
3. `[M]`/`[A]` — не доказательство функции. Функция существует только при `[L]`/`[S]`/`[D]`; `[D]` — только endpoint, не поведение.
4. Headless-парсер ≠ работающая функция; live-функция требует E3.
5. Нельзя менять тест под код, ослаблять assert, удалять проверки или объявлять skip успехом.
6. Секреты/токены/ключи не попадают в evidence; редакция обязательна.
7. **Только дамп или рабочее приложение.** Не использовать память модели, чужие версии и веб-догадки как источник поведения Discord; версия фиксируется (`1.0.162` dump / `1.0.166` installed) и расхождение — `version-gap`.

## 5. Приоритеты и срочность

### 5.1 Классы

| Класс | Критерий | Реакция |
|---|---|---|
| **P0** | блокирует live/безопасность/юр. риск; утечка; краш ядра | stop-the-line, 1 воркер, окно PM |
| **P1** | ежедневный паритет: серверы, голос, сообщения, навигация | 2 воркера max |
| **P2** | вторичный паритет: темы, i18n, уведомления, профиль | после P1 |
| **P3** | полировка, редкие функции | backlog |

### 5.2 Оценка внутри P1/P2 (WSJF-lite)

```
score = (business_value + time_criticality + risk_reduction) / job_size
```

- `business_value` 1–5: насколько функция нужна ежедневно;
- `time_criticality` 1–5: блокирует ли другие задачи/релиз;
- `risk_reduction` 1–5: снижает ли security/стабильность;
- `job_size` 1–5: 1 = S, 5 = XL.

`confidence` < 0.5 → сначала RE-spike, не реализация.
P0 всегда выше любого score. P3 не прыгает через P1 без письменного решения PM.

### 5.3 WIP и очереди

- ≤2 кодовых воркера одновременно.
- 1 REA/G6-сессия + 1 design + 2 code = максимум.
- Один `cargo` на target-dir.
- Live-окно — ровно 1 на приёмку, кэшируется по UI+binary key.
- 2 одинаковых отказа → смена подхода; 3-я попытка запрещена.

## 6. Процесс G6 (Definition of Done)

1. **Inventory**: REA/дамп → список функций и evidence.
2. **Compare**: текущее приложение → `implemented/partial/absent/unknown`.
3. **Gap card**: ID, source, evidence, gap, DoD, test, owner, priority.
4. **Priority**: P0–P3 + WSJF; зависимость и окно.
5. **Handoff**: G1/G2/G3/G5 получают карточку с файлами и границами.
6. **Red**: тест/оракул падает по правильной причине.
7. **Green**: минимальный код; тесты не ослаблены.
8. **G6 verify**: matrix row обновлена; `parity-ok` или `deferred` с причиной.
9. **PM accept**: только с evidence; иначе возврат.
10. **Docs**: после accepted, не в red-фазе.

## 8. Гейт G6

PM **не принимает** задачу, если:

- нет строки в матрице;
- `source` не указан или E0;
- `[A]` выдан за `[L]/[S]/[D]` или за существующую функцию;
- тест ослаблен/скипнут без waiver;
- live-функция без E3;
- G6 reviewer не подтвердил паритет (или не зафиксировал deferred).

## 10. Запреты

- не запускать Discord live без окна PM;
- не захватывать чужие микрофон/экран/данные;
- не писать в `logs/`, `functions/`, `evidence/`, `/home/sanya/re-deep`, установленный Discord;

- не коммитить (координатор);
- не объявлять функцию готовой по одному парсеру.

## 11. Source-only: только дамп или рабочее приложение

1. Источник поведения — **только** `app.asar`/ELF установленного Discord, dump `re-deep`
   или live-захват. Не память модели, не сторонние сайты, не «в Discord обычно так».
2. Каждая функция получает `source` и `level`; без этого строка не попадает в матрицу.
3. `[D]` (Enum-запись) подтверждает только наличие endpoint, не payload/поведение.
4. `[M]`/`[A]` не могут создать новую функцию; только уточнить дизайн/приоритет.
5. Версия: dump **1.0.162**, установленный клиент **1.0.166**. Любое расхождение —
   `version-gap` с отдельной проверкой, не «обновим по памяти».
6. Контракт считается готовым к коду при `[L]` (live) или `[S]` (call-site с телом/схемой);
   для `[D]` — только RE-задача, не реализация.
7. Перед кодом G6 Reviewer проверяет: source существует, цитата точная, тег не завышен.

## 12. Test integrity: тесты не ослаблять и не обходить

1. Red-first: тест падает по правильной причине; лог сохраняется.
2. Запрещено: `.only`, `.skip` без waiver, `todo`, пустые assert, удаление проверок,
   ослабление допусков, подмена реального поведения моком.
3. Тест-оракул — независимый источник: dump, fixture, jq/awk/md5, эталонные байты.
4. Нельзя «пройти мимо теста»: `gate:release` обязателен; e2e skip ≠ pass.
5. Любое изменение теста проверяет G6 Reviewer; ослабление = P0 и возврат.
6. Для критичных контрактов — mutation check: мутация продукта должна ронять тест.
7. G6 не принимает задачу, если diff тестов уменьшает покрытие проверяемого контракта.
