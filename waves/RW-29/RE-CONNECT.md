# RE-CONNECT — доказательная база политики reconnect/resume (W29c)

Волна RW-29, карточка P4-12 (устойчивость, авто-rejoin). Модуль:
`rust/crates/discord-voice/src/reconnect.rs`. Сеть, live Discord, таймеры и Frida не
использовались: всё ниже — цитаты уже снятых RE-артефактов (только чтение) и выводы из них.

## 2. Что наблюдается в захвате (§4)

1. **`op7 RECONNECT` — ровно один раз.** Цитата (§4):
   > «`op7 RECONNECT` — подтверждён 1×: сокет `.10029` получил `op:7` (терм `t=nil`, s=nil)
   > после s=331; сервер инициировал реконнект → клиент закрыл `.10029`
   > (ts `1792397049679`) и открыл `.13072` (ts `1792397049498`) с **RESUME → RESUMED
   > s=332** — серия `s` продолжается без разрывов.»

   Вывод для политики: разрыв сокета не означает новую сессию — базовое действие
   `Resume`, и только отказ сервера переводит клиента в `Identify`.

2. **Три эпизода resume, все успешные.** Таблица §4: `.8269` — `s 95..663`,
   `.8608` — `s 664..722`, `.13072` — `s 332..371`, «Первый диспатч» —
   `GUILD_MEMBER_LIST_UPDATE / GUILD_MEMBER_LIST_UPDATE / RESUMED`. Итог по диспатчам:
   `RESUMED 3`. Разрывов `s` нет ни на одном сокете (§4: «Разрывов `s` нет ни на одном
   сокете»).

3. **Клиентские паузы между сокетами — секунды, не миллисекунды.** §4:
   > «Ранее были два переподключения **без** op7 в захвате (`.5532`→`.8269` и
   > `.8269`→`.8608`, клиент открывал новый сокет через ~2.9 с после закрытия старого,
   > серии s 95 и 664 без разрывов).»

   Наша первая ступень `BACKOFF_MS[0] = 1000` мс и потолок `30 000` мс согласуются с
   порядком наблюдаемого (~2.9 с), но не являются его измерением.

4. **`op9 INVALID_SESSION` не наблюдался.** §4: «`op9 INVALID_SESSION` не наблюдался»;
   §9.3: «`op9 INVALID_SESSION`, а также MLS/DAVE-опкоды … в захватах не встречались».
   Ветка `on_invalid_session` → `Identify` взята из протокола (RESUME отклонён ⇒ нужен
   IDENTIFY), а не из измерения. Поэтому задержка `INVALID_SESSION_DELAY_MS = 1 000` мс —
   наше детерминированное решение, а не воспроизведённое значение Discord.

5. **Соединение живое и после resume.** `HELLO.d.heartbeat_interval = 41250` мс на всех
   7 сокетах; `op11 ACK` — 196 суммарно. Значит `on_established` (READY/RESUMED) — штатная
   точка сброса счётчика попыток, а не только «первый логин».

6. **Исходящие кадры недоступны.** §4: «бинарные кадры маскированы (`len+sha256`),
   содержимое недоступно»; длины 173/176 Б интерпретируются как RESUME, 943 Б — IDENTIFY.
   Отсюда ограничение: содержимое RESUME/IDENTIFY и клиентские таймауты не проверяемы по
   захвату, модуль моделирует только решение и задержку.

## 3. Как это отображено в контракте (TZ §1) и тестах

| Наблюдение / требование | Правило политики | Кейс |
|---|---|---|
| Разрыв не рвёт `s` → сперва RESUME | `on_disconnect(true)` → `Resume`, `BACKOFF_MS[min(attempt,5)]` | r01, r02 |
| Повторные разрывы → нарастающая пауза | таблица `1000/2000/4000/8000/16000/30000`, потолок на последнем элементе | r02, r10 |
| Защита от бесконечного цикла | `attempt >= max_attempts` → `GiveUp`, `delay_ms = 0` | r03, r07, r09 |
| RESUME отклонён (op9) → новая сессия | `on_invalid_session()` → `Identify`, `INVALID_SESSION_DELAY_MS`, `attempt += 1` | r04, r09 |
| READY/RESUMED — штатное состояние | `on_established()` → `attempt = 0` | r05, r08 |
| Сессия не продолжается (не resumable) | `on_disconnect(false)` → `Identify` с тем же бэкоффом | r06 |
| Лимит 0 бессмыслен | `new(0)` → `max_attempts = 1` | r07 |
| Переиспользование после `GiveUp` | `on_established()` возвращает политику в работу | r08 |

Счётчик `attempt` — число израсходованных попыток; `ReconnectPlan.attempt` — значение
после учёта события. Насыщение — `saturating_add` на `u32::MAX`, отдельно проверено
unit-тестом в `src/reconnect.rs`.

## 4. Ограничения и что не заявляется

1. **Точные клиентские задержки Discord не измерены.** В захвате видны только паузы
   ~2.9 с между сокетами; jitter/рандомизация не наблюдались. Наш бэкофф —
   детерминированный и документированный, а не копия клиентского.
2. **`op9`-ветка нормативная, не эмпирическая.** Ни одного `INVALID_SESSION` в захватах
   нет; задержка 1000 мс выбрана нами.
3. **Wire-совместимость не заявляется.** Исходящие RESUME/IDENTIFY маскированы (§4, §9.2),
   поэтому модуль ничего не утверждает о полях кадра, кодах закрытия и `resume_gateway_url`
   (последний виден только в READY, §5).
4. **Модуль безвременной.** Задержка — чистое значение; применение таймера, закрытие
   сокета и повторное открытие соединения — вне модуля (транспорт P1-05/P4-01).
5. **Граница «голос/шлюз».** Политика описана для сессии шлюза (`op7`/`op9`, `s`); для
   голосового RTC-сокета (`op8 Hello`, heartbeat 13 750 мс) переиспользование возможно, но
   в этой карточке не проверялось.
6. **Лимит попыток — политика продукта.** В захвате нет исчерпания попыток; значение
   `max_attempts` задаёт вызывающая сторона, `new(0)` сводится к одной попытке.
