# HTTP-транспорт REST: рабочий разбор и запрос решения (2026-10-20)

**Статус:** **решено владельцем 2026-10-20 — вариант A** (ручной HTTP/1.1 на tokio+tokio-rustls;
разрешение на прямые зависимости без сетевых загрузок выдано). Разбор ниже — история вопроса;
см. §6 «Решение». Политика «честные значения» (ТЗ RW-09 §6.1) также подтверждена владельцем.
Блокировало первую живую REST-волну (P1-09/P2-06); реализация — отдельной волной после RW-09.

## 1. Вопрос

Чем отправлять реальные REST-запросы к `https://discord.com/api/v9` (HTTP/1.1 поверх TLS):

- **A** — ручной HTTP/1.1-клиент на крейтах, которые уже есть в проекте;
- **B** — `reqwest` (с `rustls-tls`);
- **C** — `hyper` (+ `hyper-rustls`);
- **D** — отложить.

## 2. Факты (проверено в репозитории 2026-10-20)

- `rust/Cargo.lock`: `reqwest`, `hyper`, `h2`, `tower`, `http-body` **отсутствуют**; из «сетевого»
  слоя есть только `http` (низкоуровневые типы, транзитивный), `httparse 1.10.1`, `bytes 1.12.1`.
- Уже есть (прямо/транзитивно, всё собрано и работает): `tokio 1.53.3`
  (`rt-multi-thread`/`macros`/`net`/`time`), `tokio-rustls 0.26.6`, `rustls 0.23.46`
  (`ring`/`std`/`tls12`), `webpki-roots 1.0.9`, `futures-util`.
- Офлайн-кэш `~/.cargo/registry/cache/*`: ни `reqwest`, ни `hyper`, ни `tower`, ни `h2`, ни
  `http-body` нет — поставить их без сетевых загрузок **нельзя**.
- Политика пакета (`rust/Cargo.toml`): новые зависимости — только с разрешения владельца;
  первая сборка (сеть) уже была, далее всё офлайн (`cargo test --offline`).
- Живые данные: Discord REST работает по HTTP/1.1; заголовки ответов — `Content-Length` (тела
  REST небольшие), сжатие включается только если запросить `Accept-Encoding` (можно не просить).

## 3. Варианты

| Вариант | Новые загрузки | Сеть | Плюсы | Минусы |
|---|---|---|---|---|
| **A. Ручной HTTP/1.1 на tokio+tokio-rustls** | 0 (в `Cargo.toml` — прямые записи на версии, уже лежащие в `Cargo.lock`) | нет | тот же TLS-стек, что у WS (один `rustls`); свои таймауты/ретраи уже готовы (`rest::retry`); полный контроль над заголовками; офлайн-тесты, включая TLS-стаб с самоподписанным сертификатом | пишем фрейминг/парсинг сами (~300–400 строк + тесты); HTTP/2 не будет (для REST не нужен); gzip не поддержан (не запрашиваем) |
| B. `reqwest` | ~25–40 крейтов (hyper, h2, tower, http-body, …) — загрузка из сети | да | минимум кода; редиректы/keep-alive из коробки | противоречит политике «без новых зависимостей»; аудит десятков крейтов; h2/tower — балласт для REST |
| C. `hyper` (+`hyper-rustls`) | ~10–15 крейтов — загрузка из сети | да | качественный HTTP/1.1-парсер | та же проблема загрузки/аудита; выигрыш против A мал |
| D. Отложить | 0 | нет | — | блокирует живые REST-волны; причин ждать нет |

## 4. Мини-план A (если одобрено)

1. `rust/Cargo.toml`: добавить прямые `tokio-rustls = "0.26"` (+ при желании `httparse`, `bytes`) —
   все версии уже в `Cargo.lock` и офлайн-кэше, **загрузок нет**; изменение манифеста — по
   разрешению владельца.
2. `rest/transport.rs`: TLS-соединение (`rustls` + `webpki-roots`), запись запроса
   (метод/путь/заголовки/тело), чтение ответа (статус, заголовки, тело по `Content-Length` и
   chunked), `Accept-Encoding` не отправляем, на первом шаге `Connection: close` (keep-alive —
   позже, при необходимости).
3. Тесты офлайн: HTTP-фрейминг — TCP-стаб на `127.0.0.1`; TLS — стаб с самоподписанным
   сертификатом (разовый fixture через `openssl`, корень добавляем в клиентский `RootCertStore`).
   Живой Discord — только ручной smoke в согласованное с владельцем окно.
4. Ретраи/таймауты — уже готовые `rest::retry`; 429/`Retry-After` — карточка P1-09.

## 5. Запрос решения

- Выбрать **A / B / C / D** (рекомендация — **A**).
- При A: разрешение добавить в `rust/Cargo.toml` прямые `tokio-rustls` (0.26) и, опционально,
  `httparse` + `bytes` — **без загрузки новых крейтов** (все версии уже в локе/офлайн-кэше).

## 6. Решение (2026-10-20, владелец)

- Транспорт: **вариант A** — ручной HTTP/1.1 на `tokio` + `tokio-rustls`; разрешено добавить в
  `rust/Cargo.toml` прямые `tokio-rustls` (0.26) и, при необходимости, `httparse`/`bytes` —
  версии уже в `Cargo.lock`, сборка офлайн, сетевых загрузок нет.
- Поля идентичности X-Super-Properties: подтверждены «свои честные значения» (ТЗ RW-09 §6.1) —
  `browser=discord-lab`, версия = версия крейта, build = 0; всё конфигурируемо.
- Следствие: волна реализации транспорта (`rest/transport.rs` + офлайн-тесты: TCP-стаб и
  TLS-стаб с самоподписанным сертификатом) планируется после RW-09 — до первой живой REST-волны
  (P1-09/P2-06).
